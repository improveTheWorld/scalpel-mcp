## 2. Contrat modifié (et pourquoi c'est légitime)

`tests/test_read_block_path.py::test_a_member_needs_a_container...` encodait l'ancien contrat : **refuser** un membre nommé sous le fichier. Ce test a été remplacé par `test_a_member_named_under_a_file_is_routed_or_refused_on_evidence`, qui vérifie les **deux** faces :

* fichier à **un seul type** -> le membre est routé dedans (0 refus, 0 tour perdu) ;
* fichier à **deux types** -> le refus demeure (l'ambiguïté est réelle), avec le message et le hint d'origine ;
* la chaîne imprimée `src/ov.cs::N::Over` continue de résoudre et d'asseoir le membre au bon niveau d'indentation.

La règle appliquée est celle demandée : *un outil qui sait exécuter la demande d'un agent d'une façon déterministe ne doit pas la refuser*. Le refus n'est conservé que là où l'évidence manque.

## 3. Découverte supplémentaire (non corrigée, à traiter)

**Insérer dans un conteneur VIDE est refusé.** `insert_symbol("f.cs::N::Over", code="public void M() {}")` sur une classe **sans aucun membre** répond
`error: ... would land outside 'f.cs::N::Over' ... actionable_hint: Insert into the container itself (position start or end of its body), not after its closing brace`.
Le hint prescrit exactement ce que l'appelant a demandé. Conséquence : le **premier** membre d'un type neuf ne peut être ajouté que par `edit_block` avec une opération de ligne. Piste : quand le conteneur n'a aucun enfant, calculer la position juste **avant** son accolade fermante (`parent_sym.end_byte` remonté au dernier `}` non blanc) au lieu de retomber sur `end_byte`. Ce cas est épinglé dans le test (le conteneur du scénario « deux types » porte un membre exprès) pour que le correctif futur soit vérifiable.
